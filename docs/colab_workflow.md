# Google Colab Workflow

## Recommended Google Drive Location

Upload or sync the full project folder to this Drive path:

```text
MyDrive/ds_portfolio/project_01_eia861m_electricity_sales/
```

In Colab, the mounted path becomes:

```text
/content/drive/MyDrive/ds_portfolio/project_01_eia861m_electricity_sales/
```

Avoid spaces and special characters in the Drive path. This keeps path handling simpler across Colab, Python, shell commands, and future GitHub documentation.

## Colab Setup

The acquisition and EDA notebooks mount Drive and detect the recommended project path automatically. If you use a separate Colab notebook, mount Drive first:

```python
from google.colab import drive
drive.mount("/content/drive")
```

Only set `PROJECT_ROOT_OVERRIDE` manually inside a notebook when your folder is in a different location. The current notebook already detects the recommended path.

## API Key Options

In Colab, store `EIA_API_KEY` in the Secrets panel and allow the notebook to access it. Run this cell before acquisition if the raw CSV is absent:

```python
from google.colab import userdata
import os
os.environ["EIA_API_KEY"] = userdata.get("EIA_API_KEY")
```

Do not paste a real key into a code cell, output, or shared Drive file. A local `.env` file is supported for private desktop runs, but keep it out of the repository and shared folders. `.env.example` documents only the variable name.

## Hybrid Run Strategy

The project is designed to avoid rerunning expensive or slow steps unnecessarily.

### Checkpoint 1: Raw API Data

Generated by:

```text
scripts/download_data.py
```

Saved to:

```text
data/raw/eia861m_retail_sales_2016_2025.csv
artifacts/metadata/eia861m_acquisition_metadata.json
```

If the raw CSV already exists, notebook 01 loads it instead of calling the API again. In contrast, `scripts/download_data.py` performs a new API fetch but refuses to overwrite an existing raw CSV by default. Use `--replace-existing` only after deliberately deciding to replace that snapshot; a clean project copy is safer for reproduction tests. Do not run the script merely to inspect an existing snapshot.

Rerun acquisition only when:

- the API query changes;
- the period changes;
- the state or sector scope changes;
- the raw file is missing or suspected stale;
- you intentionally want a fresh EIA snapshot.

### Checkpoint 2: Validation Flags

Generated by:

```text
scripts/validate_data.py
```

Saved to:

```text
data/interim/eia861m_retail_sales_2016_2025_with_quality_flags.csv
artifacts/metrics/data_validation_summary.json
```

These files can be regenerated quickly from the raw CSV. They should be regenerated whenever validation logic, tolerance settings, or raw data changes.

### Checkpoint 3: EDA Artifacts

Generated outputs should follow the same pattern:

```text
data/processed/
artifacts/metrics/
reports/figures/
```

Do not store undocumented manual outputs. Every checkpoint must have code that can regenerate it.

## Recommended Colab Execution Pattern

1. Mount Drive.
2. Set `PROJECT_ROOT_OVERRIDE`.
3. Set `EIA_API_KEY` only if raw data is not already available.
4. Run acquisition cells; notebook 01 reuses the raw CSV when present.
5. If raw CSV is absent, retrieve the key from Colab Secrets before acquisition.
6. Run validation cells.
7. Save regenerated validation flags and summary artifacts.

This gives a hybrid workflow: expensive acquisition can be reused from Drive, while validation and analysis remain reproducible.

For a clean-source rebuild and its limitations, see [Reproducibility](reproducibility.md). Testing SQL or unit tests against an existing interim CSV does not require rerunning notebook 01 or setting an API key.
